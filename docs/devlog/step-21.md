# Step 21 — 던전 하나당 World 하나


**Decision:** `Battle` 구조체로 한 판의 상태를 묶고 맵으로 보유하고(21a), 브로드캐스트를
던전별로 나누고(21b), 빈 던전을 정리한다(21c).

**Why:** Step 20 의 로그 한 줄이 알려줬다.

```
Handshake ... -> conn 3 (entity 27, user alice)
```

**엔티티 ID 가 27 이다.** 이전 파티의 몬스터들이 번호를 쓰고 갔다. 던전이 끝나도 `World` 가
그대로라, 두 번째 파티는 첫 파티의 `Failed` 상태를 물려받아 아예 못 논다.

Step 20 에서 "여러 대로 늘려도 구조가 같다"고 적어놨는데 **한 대가 한 판만 도는** 상태였다.
연동 작업의 절반이 헛돈다.

**Alternatives considered:**
- **던전이 끝나면 `World` 를 리셋**: 한 줄이면 된다. 그런데 **동시에 두 판을 못 돌린다.**
  배틀 서버 한 대가 파티 하나만 받으면 프로세스를 파티 수만큼 띄워야 한다.
- **배틀 서버를 파티마다 프로세스로**: 격리가 확실하다. 그런데 프로세스 하나당 메모리와
  포트가 필요하고, 로비가 띄우고 죽이는 책임을 져야 한다. 4인 던전 하나에 프로세스 하나는
  과하다.
- **`Battle` 을 `unique_ptr` 로**: 포인터 무효화를 피할 수 있다. 그런데 `unordered_map` 은
  노드 기반이라 **원소를 재배치하지 않는다.** 값으로 둬도 참조가 안전하다. 16c 에서
  `monsters_` 가 `vector` 라 포인터를 조심했던 것과 반대 상황이다.

**전역 멤버가 곧 "하나뿐"이라는 가정이었다.** 옮긴 것들을 보면 그게 드러난다.

```
world_            ->  Battle::world
battle_id_        ->  Battle::id
roster_           ->  Battle::roster
last_phase_       ->  Battle::last_phase
last_room_state_  ->  Battle::last_room_state
```

다섯 개가 전부 "던전마다 하나씩" 있어야 하는 것들이었다. 16 편에서 `Player` 를 `Connection`
에서 꺼낸 것과 **같은 종류의 작업**이고, 그때처럼 **코드가 시점을 알려줬다** — 그때는 "연결
없는 객체(몬스터)"가 신호였고, 이번엔 엔티티 ID 27 이었다.

**브로드캐스트에 `continue` 한 줄이 늘었다.**

```cpp
for (auto& ce : connections_) {
    if (ce.second.battle_id != b.id) continue;
    send_to(ce.second, ...);
}
```

던전 × 연결 이중 루프다. 10판 × 40연결이면 틱당 400번. 지금은 공짜이고, 커지면 `Battle` 이
자기 연결 목록을 들어야 한다 — 그러면 연결이 끊길 때 거기서도 지워야 한다. 16a 의 "소유권을
나누면 해제도 나뉜다"가 또 나온다. **재기 전에는 안 한다**(19 편).

**순서가 메모리를 아껴준다.** 던전마다 `snapshot_buffer_` 를 다시 채우는데, 한 던전을 다
보내고 다음으로 넘어가기 때문에 간섭이 없다. "모든 던전의 스냅샷을 만들어두고 한꺼번에
보내기"로 짰다면 버퍼가 던전 수만큼 필요했을 것이다.

**`abandoned` 라는 세 번째 결과.** 지금까지는 `wipe` 뿐이었다. 전멸 전에 다들 나가면 결과를
못 보내고 있었는데, 빈 던전을 정리하면서 보낼 자리가 생겼다.

실측에서 **끊긴 뒤에도 명단이 남아** `players=[erin, frank]` 가 나왔다. 18d 에서 "명단은
접속자 목록이 아니라 기록"이라고 만든 것이 여기서 값을 했다.

`clear` 는 아직 없다 — 던전에 끝이 없어서 보낼 조건이 없다.

**세 번째로 "발급되지 않는 값"을 sentinel 로 썼다.**

| 곳 | 값 | 가능한 이유 |
|---|---|---|
| 16b 문 엔티티 | `id = 0` | `World` 가 1부터 발급 |
| 17a 웨이브 시작 | `wave_index = -1` | 음수 웨이브가 없음 |
| 21c 유휴 시계 | `empty_since = epoch` | `steady_clock` 의 epoch 가 안 나옴 |

반대로 14a 에서는 못 썼다 — 패킷 번호 0 이 **유효한 값**이라서 플래그를 따로 뒀다. 매번
판단 기준은 하나다: **그 범위에 유효한 값이 있느냐.**

**현재 한계 (의도적):**
- **`clear` 결과가 없다** — 던전에 끝이 없다. 보스방과 종료 조건이 생겨야 한다.
- **재접속이 안 된다** — 토큰이 1회용이고 주소로 연결을 찾는다. 15초 유예를 둔 건 이걸
  고칠 때를 위한 것인데, **지금은 쓰이지 않는 유연성**이다.
- **던전 × 연결 이중 루프** — 재기 전에는 안 고친다.
- **로비가 배틀 서버를 한 대만 안다** — 여러 대로 늘리려면 로비가 분배해야 한다.
- **던전이 몇 개까지 되는지 안 쟀다** — 19 편의 봇은 전부 익명 던전 하나에 모인다.
  던전 N개를 만드는 부하 테스트가 따로 필요하다.

**검증:** 도커 compose + 로비 클라 2쌍 + 토큰으로 입장한 UDP 피어 4개.

*던전 분리 (21a, 21b)*
1. 파티 둘이 `battleId=5` / `battleId=6` 으로 갈림
2. **엔티티 ID 가 던전마다 1부터** — battle 5 도 battle 6 도 `entity 1, 2`
3. 양쪽 모두 스냅샷 엔티티 **22개**. 남의 던전이 안 보임
4. `[battle 5]` / `[battle 6]` 이 각자 `kills=5` 를 따로 셈
5. 전멸도 각자 `FAILED`

*정리 (21c)*
6. 전멸 후 결과가 던전별로 각각 — `battle=5 [alice,bob]`, `battle=6 [carol,dave]`
7. 15초 뒤 `[battle N] closed`, 상태 로그가 사라짐
8. 전멸로 이미 보고한 던전은 **다시 보내지 않음** (`reported` 플래그)
9. 전멸 전에 모두 나간 던전 → `result=abandoned`, `kills=9`, `players=[erin, frank]`
   (두 사람 다 이미 타임아웃으로 사라진 뒤)
