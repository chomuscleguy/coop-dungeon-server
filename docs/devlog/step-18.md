# Step 18 — 다운과 부활: 던전이 끝나는 길


**Decision:** 플레이어 체력과 몬스터 접촉 공격으로 Down 을 만들고(18a), 채널링 부활과
10초 블리드아웃을 붙이고(18b), 전원 다운을 `Failed` 로 판정하고(18c), 결과를 로비에
보내고(18d), 두 서버를 같이 띄운다(18e).

**Why:** 지금까지 던전은 **끝나지 않았다.** 방이 무한히 이어지고, 몬스터가 닿아도 아무 일이
없었다. 끝나는 길이 생겨야 "로비로 돌아간다"가 성립하고, 그래야 13편에서 서버를 둘로
나누며 미뤄둔 **연동**을 할 수 있다.

**설계 결정 셋은 사용자가 정했다** (2026-10-06): 부활은 채널링, Down 은 10초 뒤 Dead,
전멸하면 `Failed` 로 두고 정지.

**Alternatives considered:**
- **즉시 부활**: 구현이 가장 단순하고 전투 흐름이 안 끊긴다. 그런데 "구하러 갈지 말지"라는
  선택이 사라진다. 채널링은 **구하는 쪽도 그동안 맞는다** — 실측에서 구조자 체력이
  85 → 73 → 55 로 깎였다.
- **Dead 없이 Down 만**: 단순하다. 그런데 Down 에 시간 압박이 없어서 "천천히 구하면 된다"가
  된다.
- **배틀 서버에 JSON 라이브러리 추가**: 로비와 말이 맞는다. 그런데 **쓰기만 하고 읽지 않고**,
  내용이 전부 정수와 고정 문자열이다. 의존성·vcpkg·Dockerfile 을 건드릴 값어치가 없다.

**스냅샷이 처음으로 커졌다.** 9 → 11바이트, 154개 → 126개. 클라이언트가 쓰러진 동료를 다르게
그려야 하고 체력바도 필요해서다. 20마리를 쓰는 지금은 여전히 넉넉하고, **비트를 아끼는 건
아낄 이유가 생겼을 때** 한다(17편의 1400바이트 논의와 같은 결론).

**한 칸을 둘이 나눠 쓴 자리가 하나 있다.** 쓰러진 플레이어의 `hp_pct` 는 체력이 아니라
**부활 진행도**를 나른다. 체력은 어차피 0이라 자리가 비어 있다.

```cpp
if (life == EntityLife::Down) return 부활 진행도;
return 체력 비율;
```

**두 값이 동시에 의미를 가질 수 없을 때**만 쓸 수 있는 수법이다. 16b 에서 엔티티 타입을
ID 범위가 아니라 명시적 필드로 둔 것과 반대 방향인데, 차이는 "상태로 구분이 명확한가"다.
여기서는 같은 패킷의 `life` 가 답을 준다. 다만 **클라이언트에도 같은 규칙이 박혀야** 하고,
둘 중 하나만 고치면 조용히 깨진다.

**쓰러진 사람을 몬스터가 쫓지 않게 했다.** 없으면 몬스터가 쓰러진 사람 위에 앉아 있고,
구하러 가면 그 떼를 전부 상대해야 해서 구조가 사실상 불가능해진다. 몬스터가 다음 희생자를
찾아 떠나야 **틈이 생긴다.**

**16c 의 "몬스터가 뭉친다"가 그림 문제에서 밸런스 문제가 됐다.** 20마리가 한 점에 있으니
한 번에 20대를 맞는다 — 초당 60, 100hp 면 1.7초다. 서로 밀어냈다면 3~4마리만 닿았을 것이다.
가만히 서 있으면 죽는 건 뱀서류에서 맞는 동작이지만 지금은 **뭉침 때문에 과장돼 있다.**
수치를 고치기 전에 뭉침을 고쳐야 한다.

**사망 타이머를 멈추지 않기로 한 것이 설계의 핵심이다.** 멈추면 "일단 붙기만 하면 안전"이
되어 10초 중 9초를 흘려보내도 된다. 멈추지 않으니 **7초 안에 도착**해야 3초 채널링이 끝난다.

반대로 부활 진행도는 **0으로 날리지 않는다.** 몬스터에 밀려 한 발짝 물러서는 건 정상적인
플레이다. 17b 의 "과반수가 깨지면 카운트다운 즉시 취소"와 가혹함의 정도를 다르게 잡았는데,
방 전환은 되돌릴 수 있지만 **구조는 실패하면 사람이 죽기** 때문이다.

**전멸 판정을 다운 처리 뒤에 둔 이유.** 순서를 바꾸면 한 틱 늦게 판정되고, 그 한 틱 동안
몬스터가 한 번 더 때린다. 33ms 라 눈에는 안 보이지만, 나중에 "마지막 타격자" 같은 걸
기록하면 틀린다.

**`Failed` 면 `update` 전체가 맨 앞에서 돌아선다.** `update_phase` 만 막는 게 아니다.
결과 화면 뒤에서 몬스터가 계속 움직이면 **배경이 살아 있는 결과 화면**이 된다. 17a 의
`players_.empty()` 가드와 짝인데, 거기는 "아직 안 시작"이고 여기는 "이미 끝남" —
**양쪽 끝을 다 막아야** 월드가 의도한 구간에서만 흐른다.

부수 효과가 하나 생겼다. 전멸하면 쓰러진 사람들이 **Down 상태 그대로 굳는다.** 10초가
지나도 Dead 가 안 된다. 결과 화면이 흔들리지 않는다는 점에서 맞는 동작인데, **의도해서 그렇게
한 게 아니라 `update` 를 통째로 멈춰서 생긴 결과**다.

**JSON 라이브러리를 안 넣었다.** 배틀 서버가 로비에 보내는 건 한 통뿐이고, 전부 정수와 고정
문자열이다.

```cpp
os << "{\"type\":\"DungeonResult\",\"data\":{" << "\"kills\":" << world_.total_kills << ...
```

**직렬화만 필요하면 라이브러리가 필요 없을 수도 있다.** 단, 시크릿을 넣으면서 문자열이 하나
들어갔고, **아까 적어둔 한계에 정확히 걸리는 자리**가 됐다. 환경변수에 따옴표나 역슬래시가
들어가면 깨진다. 지금은 우리가 정하는 값이라 괜찮을 뿐이다.

**로비 전송은 실패해도 되게 만들었다.** 재시도도 없고 예외도 없고 전투에 영향도 없다.
실측에서 DNS 조회가 실패하는 동안에도 틱이 **30/s, 지터 0.28ms** 를 유지했다 — 동기
`resolve` 였다면 거기서 수십~수백 ms 가 멈췄을 것이다.

그 덕에 `depends_on` 만으로 충분해졌다. 그건 시작 순서만 정하고 "준비될 때까지"가 아닌데,
배틀 서버가 던전이 끝날 때만 접속하고 실패해도 넘어가니 상관없다. **실패해도 되게 만들어두면
오케스트레이션이 단순해진다.**

**로그인 없이 받는 경로를 열었고, 그래서 막아야 했다.** 로비는 `Login` 말고 전부 로그인을
요구하는데 배틀 서버는 사람이 아니라 로그인할 수 없다. 그냥 열면 **누구나 7777 에 붙어
`kills=9999` 를 밀어 넣을 수 있다.**

공유 시크릿으로 막았고, 틀리면 **응답조차 하지 않는다.** `send_error("bad secret")` 를 보내면
공격자에게 "시크릿이 있다"와 "틀렸다"를 알려준다. 13a 의 "모르는 주소에 응답하지 않는다"와
같은 생각이다.

충분한 보안은 아니다. 평문이고, 제대로 하려면 수신 포트를 내부 네트워크에만 열어야 한다.
지금 목표는 **"아무나"를 "같은 네트워크 안에서만"으로 줄이는 것**이다. 보상이 없어서 피해도
없지만, **공짜로 막을 수 있을 때 막아두면** 보상이 생겼을 때 이미 막혀 있다.

**Dockerfile 을 하나에 몰아 쓸 뻔했다.** 배틀 서버 스테이지를 로비 `Dockerfile` 뒤에 붙이면
문법은 맞고 **빌드도 통과한다** — 멀티 스테이지가 원래 `FROM` 을 여러 번 쓰니까. 그런데
**마지막 스테이지가 최종 이미지**라, `docker build .` 하면 로비 이미지 자리에 배틀 서버가
나온다. 에러 없이 틀리는 종류라 `--target` 을 쓰지 않는 한 눈치채기 어렵다.

**현재 한계 (의도적):**
- **결과에 누구의 던전인지가 없다** — 배틀 서버는 엔티티 ID 만 알고 계정을 모른다. 로비가
  "이 파티가 이 배틀 서버로 간다"를 알려주는 경로가 없다. **로비 → 배틀 방향**이고 매칭
  설계가 먼저라 뒤로 미뤘다. 보상을 주려면 반드시 필요하다.
- **결과를 큐에 쌓지 않는다** — 로비 재시작 중에 끝난 던전의 결과는 사라진다. 잃을 보상이
  없어서 안 만들었다.
- **TCP 를 믿는다** — `async_write` 가 성공하면 도착했다고 본다. 로비가 받고 처리하다 죽으면
  결과가 사라진다. 로비의 ack 를 기다리는 건 보상이 생길 때 할 일이다.
- **클리어 결과가 없다** — 던전에 끝이 없어서 `result:"clear"` 를 보낼 조건이 없다.
- **방 전환 시 전원 회복** — 길이가 무한이라 회복이 없으면 언젠가 반드시 죽는다. 길이가
  정해지면 다시 볼 값이다.
- **난이도가 인원수와 무관** — 받는 피해는 1/N 로 줄고 주는 피해는 N 배라 **난이도가 인원의
  제곱으로 쉬워진다.** `monsters_for_wave` 에 인원수가 들어가야 한다.

**검증:** 도커 컨테이너(두 서버 compose) + 직접 조립한 UDP/TCP 패킷.

*체력과 Down (18a)*
1. 1인 정지 → `hp 100 → 40 → 0`, 12초에 `DOWN`
2. 도망친 플레이어는 30초간 **9 피해**, 선 플레이어는 사망 — "계속 움직여라"가 규칙으로 성립
3. Down 후 몬스터가 **정지** (쫓을 대상 없음)
4. 2인일 때는 몬스터가 갈라져서 **아무도 안 쓰러짐** → 인원수 밸런스 문제를 드러냄

*부활 (18b)*
5. 진행도 `12 → 46 → 81` (초당 34%), **3초**에 완료
6. 부활 체력 **50** (절반)
7. 구조자 체력 `85 → 73 → 55` — **구하는 쪽도 깎인다**
8. 아무도 안 오면 `DOWN` 후 **정확히 10초**에 `DEAD`

*전멸 (18c)*
9. `Down` 되는 **같은 틱**에 `WIPED at room 0 wave 0 (kills 3)`
10. 그 뒤 17초간 몬스터 9마리가 `M2(0,0)` 에서 **좌표 한 칸도 안 움직임**
11. 10초가 지나도 `Dead` 전환 **안 일어남** (`update` 가 통째로 멈춰서)

*로비 전송 (18d)*
12. 로비 없이 전멸 → `resolve failed` 로그만 남고 **틱 30/s 유지**
13. `[lobby] ->` 가 **딱 한 줄** (30Hz 로 안 쏨)

*연동 (18e)*
14. compose 로 두 서버 구동 → 전멸 → 로비 로그에
    `[dungeon] result=wipe room=0 wave=0 kills=3 players=1`
15. 시크릿 없음 / 틀림 → **둘 다 거부**, 응답 없음
16. 시크릿 맞음 → 통과
