# Step 20 — 두 서버가 한 바퀴를 돈다


**Decision:** 배틀이 로비에 TCP 지속 연결을 맺고(20a), 로비가 그 연결을 배틀 서버로
인식하고(20b), 1회용 토큰으로 입장을 통제하고(20c), 결과에 참가자 이름을 담는다(20d).

**Why:** 18 편에서 결과를 로비로 보냈는데 **"누구의 던전인지"가 없었다.** 배틀 서버는 엔티티
ID 만 알고 계정을 모른다. 로비가 "이 파티가 간다"를 알려주는 경로가 없었기 때문이다.
보상을 주려면 반드시 필요한 구간이고, 유니티 클라이언트를 만들기 전에 프로토콜이 정해져야
한다.

**Alternatives considered:**
- **배틀에 TCP 리스너 추가**: 로비가 배틀에 접속한다. 그런데 포트가 하나 더 늘고, 로비가
  배틀의 주소를 알아야 하며, NAT 뒤에 있으면 못 간다.
- **로비가 배틀의 UDP 포트로 관리 패킷**: 포트 재사용은 좋은데 **유실되면 파티가 입장을
  못 한다.** 입장권은 재전송 로직을 또 만들 만한 것이 아니다.
- **18d 처럼 매번 붙었다 끊기**: 역방향이 불가능하다. 로비가 먼저 말을 걸 수 없다.

**한 방향 연결이 두 방향 통신을 만든다.** 배틀이 로비에 붙어 **유지**하면, 로비는 그 연결로
밀어 넣기만 하면 된다. 방화벽·NAT 관점에서 유리하고, 로비가 자연스럽게 "붙어 있는 배틀 서버
목록"을 갖게 되어 **여러 대로 늘려도 구조가 같다.**

**Step 4 를 반대 입장에서 다시 만들었다.** 길이-prefix 프레이밍, 송신 큐, 길이 상한 검사 —
로비 `Session` 에 만든 것과 같은 코드를 이번엔 **클라이언트 쪽**에 만들었다.

```cpp
send_queue_.push_back(std::move(frame));
if (!writing_) do_write();
```

`async_write` 가 끝나기 전에 또 쓰면 두 메시지가 섞인다. 서버를 만들 때는 "클라이언트도 이게
필요하겠구나"를 생각하지 않았다. **같은 문제가 양쪽에 다 있다.**

길이 상한도 다시 뒀다. 로비는 우리 편이지만 **프레임이 어긋나면 본문 중간의 4바이트를 길이로
읽는다.** 상대를 믿느냐와 무관하게 파싱은 방어적이어야 한다.

**읽기를 항상 걸어두는 것이 연결 감시다.** 로비를 껐을 때 `read header failed` 로 즉시 끊김을
감지했다. 쓰기는 보낼 것이 없어서 안 불렸다.

UDP 에서는 이게 안 돼서 하트비트/타임아웃을 직접 만들었다(13 편). **같은 문제를 TCP 는 공짜로
풀어준다** — 서버 사이 연결에 TCP 를 쓴 이유 중 하나다.

**끊겨 있을 때 쌓아두지 않는다.** 재연결 때 몰아서 보내는 쪽이 친절해 보이지만, 대부분은 이미
낡은 소식이고 **쌓이는 큐는 상한 없는 메모리**다. 18d 의 "실패해도 되게 만든다"의 연장이다.

**1회용 토큰, 그리고 멱등성과의 충돌.** 토큰은 쓰는 즉시 지운다. 그런데 `HandshakeAck` 이
유실되면 클라가 다시 보내는데 그때 표는 없다.

```cpp
Connection* existing = find_connection(from);
if (existing) { /* 토큰을 아예 보지 않는다 */ }
```

주소가 이미 등록돼 있으면 토큰 검사를 건너뛴다. **13 편에서 핸드셰이크를 멱등하게 만들어둔
것이 여기서 토큰 소비와 맞물린다.** 그때는 "세션이 둘 생기는 것"을 막으려던 것이었는데,
지금은 "표가 없어서 못 들어오는 것"을 막는다.

**거부할 때 응답하지 않는다.** 모르는 토큰에 "틀렸다"고 알려주면 무작위로 찔러보는 쪽에
피드백을 준다. 13a 의 "모르는 주소에 응답하지 않는다"와 같은 생각이다.

다만 **로그는 남긴다.** 잘못된 패킷(13a)과 달리 이건 드물게 일어나야 정상이라, 자주 찍히면
그 자체가 신호다.

**안전한 쪽을 기본으로 두면 테스트가 불편해진다.** `BATTLE_ALLOW_ANONYMOUS` 의 기본은 꺼짐이다.
반대로 했으면 언젠가 끄는 걸 잊은 서버가 뜬다. 대가는 **기존 테스트가 전부 깨진다**는 것이고,
봇도 PowerShell 스크립트도 `-e BATTLE_ALLOW_ANONYMOUS=1` 을 붙여야 한다. 그 불편이 비용이다.

**결정이 두 번 뒤집혔고, 매번 근거가 있었다.** 18d 에서 JSON 라이브러리를 안 넣은 근거는
"쓰기만 한다"였다. 20c 에서 읽기가 생겨 넣었고, 20d 에서 사용자 이름이 들어오면서 쓰기도
라이브러리로 바꿨다.

18d 에 **"문자열이 들어오면 이 방식은 못 쓴다"**고 적어둔 것이 효과를 봤다. 적어두지 않았다면
"전에 그렇게 했으니까"로 밀고 갔을 것이고, 사용자 이름에 따옴표가 하나 들어가는 날 깨졌을
것이다. **근거 없이 미룬 결정은 바꿀 근거도 없다.**

**1,600줄 한 파일의 마찰.** `Session` 이 `Server` 보다 먼저 정의되어 있어서, `server_.xxx()` 를
쓰는 `Session` 메서드는 **클래스 안에 본문을 둘 수 없다.** 선언만 두고 정의는 파일 아래쪽에
`void Session::xxx()` 로 쓴다 — 파일이 원래 그렇게 돼 있는데, 작업 중에 그걸 잊고 클래스 안에
넣으라고 안내해서 두 번 되돌렸다.

"어느 클래스 안"을 줄 번호로 짚기 어려운 것도 같은 원인이다. 로비를 파일로 나누면 사라질
마찰이고, **Step 21 후보**다.

**현재 한계 (의도적):**
- **배틀 서버 하나가 한 던전만 돈다** — `World` 가 전역이라 던전이 끝나도 리셋되지 않는다.
  두 번째 파티가 첫 파티의 `Failed` 상태를 물려받아 아예 못 논다. 로그에서 엔티티 ID 가 27 부터
  시작하는 것으로 드러났다. **`battle_id` 별로 `World` 를 하나씩** 가져야 한다.
- **배틀 서버가 자기 공인 주소를 모른다** — 컨테이너 안에서는 172.19.x.x 다. 로비가
  `BATTLE_PUBLIC_HOST` 로 알고 있는다. 여러 대로 늘릴 때 제대로 풀어야 한다.
- **로비가 배틀 서버를 한 대만 상정한다** — `battle_link_` 가 하나다.
- **토큰에 유효기간이 없다** — 발급 후 안 쓰면 `pending_` 에 영원히 남는다.
- **로그인 없이 받는 경로가 둘** — `BattleRegister` 와 `DungeonResult`. 예외가 늘면 언젠가
  하나를 빠뜨린다. 관리 포트를 따로 열고 외부에 노출하지 않는 쪽이 맞다 (18e 에 적어둔 그대로).
- **매칭과 연결되지 않았다** — `BattleStart` 를 방의 누군가가 직접 보낸다. Step 8 의 매칭 큐가
  파티를 만들면 자동으로 시작하는 쪽이 자연스럽다.

**검증:** 도커 compose 로 두 서버 구동 + PowerShell 로비 클라 + 직접 조립한 UDP 패킷.

*지속 연결 (20a)*
1. 초기 연결 성공
2. 로비를 끄면 `disconnected: read header failed`, 다시 켜면 **자동 재연결**
3. 끊긴 8초 동안 배틀 틱 **30/s 유지**, 지터 0.1ms 이하

*등록 (20b)*
4. `BattleRegister` → 로비에 `[battle] server registered (udp port 7778)`
5. 재연결 때 `on_connected` 가 다시 불려 등록이 **자동 복구**

*토큰 (20c)*
6. 토큰 없이 → `Handshake rejected` 26회, 스냅샷 0
7. `BATTLE_ALLOW_ANONYMOUS=1` → `user <anon>` 으로 입장, 30/s 정상
8. 진짜 토큰 → **응답 받음**, 로그에 `user alice`
9. 가짜 토큰 → **응답 없음**
10. 쓴 토큰 재사용 → **응답 없음**

*결과 귀속 (20d)*
11. `BattleStart` → alice `46c021458217f26e`, bob `2e238fed10ba683d` (서로 다른 표)
12. 배틀에 `SessionGrant battle=2 players=2`
13. 전멸 후
    `[dungeon] battle=2 result=wipe room=0 wave=0 kills=5 players=[alice, bob]`
