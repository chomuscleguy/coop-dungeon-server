# Step 23 — 보는 클라이언트

**Decision:** 유니티 클라이언트를 만들어 **스냅샷을 화면에 그리고**(23d) **입력을 30Hz로
보낸다**(23e). 프로토콜을 C#으로 옮기고(23a), 소켓을 붙이고(23b), ack 을 돌려준다(23c).

**Why:** 22편을 이렇게 끝냈다 — *"밸런스는 화면을 보면서 만질 일이라 클라이언트가 생긴 뒤로
미뤘다"*. 클리어가 불가능하다는 건 알았지만 **왜 불가능한지는 추측**이었다. 로그가 주는 건
`kills 0`, `result=wipe` 뿐이고, 그 사이에 무슨 일이 일어나는지는 안 보인다.

**Alternatives considered:**
- **C++ 봇을 늘려 ASCII로 그리기**: 도구가 이미 있고 하루면 된다. 그런데 봇은 19b 에서
  **일부러 `Connection` 을 안 쓰게** 만든 거울-테스트 회피용이다. 거기에 화면을 얹으면
  테스트 도구가 게임 클라로 변한다. 그리고 유니티 클라는 **어차피 만들어야 한다.**
- **로비 TCP 클라부터**: 로그인 → 방 → `BattleStart` → 토큰이 정석 순서다. 그런데 지금
  보고 싶은 건 **전투 화면**이고, 20c 에서 만든 `BATTLE_ALLOW_ANONYMOUS` 가 정확히 이
  상황을 위한 우회로다.
- **보간을 처음부터 넣기**: 30Hz 를 60fps 로 그리면 두 프레임에 한 번씩 움직인다. 그런데
  **끊김을 본 적이 없으면 보간이 무엇을 고치는지 모른다.** 먼저 보고 나서 넣는다.

## 한글 경로가 유니티를 막았다

`unity command eval` 이 코드와 무관하게 항상 실패했다.

```
Compilation Failed: Illegal byte sequence encounted in the input.(0행, 0열)
```

한참 헤맨 이유는 **구조화된 명령은 전부 정상이었기 때문**이다. `unity open`,
`unity status`, 씬 조작 — 다 됐다. `eval` 만 안 됐다. 그래서 C# 코드를 의심했다.

ASCII 경로에 빈 프로젝트를 하나 만들어 `eval 'return 40+2;'` 를 던져보니 **42** 가 나왔다.
원인은 레포 경로의 한글(`직접만드는`)이었다. 레포를 `coop-dungeon-server` 로 옮겼고,
그 뒤로 `eval` 이 동작한다.

> 폴더 통째 `Move-Item` 은 끝까지 실패했다(디렉터리 핸들). **새 폴더를 만들고 내용물을
> 하나씩 옮기니** 14개 전부 성공했다. 잠긴 것은 디렉터리 자체였지 그 안의 것들이 아니었다.

## ack 과 하트비트는 같이 가야 한다

소켓을 붙이고 핸드셰이크까지 되자 **5초마다 끊겼다.** 예상한 일이었다 — 받기만 하고
아무것도 안 보내니 서버가 죽은 걸로 본다. 덤으로 하나 더 나왔다.

```
[conn 1] RETRY HandshakeAck try=2
[conn 1] RETRY HandshakeAck try=3
[conn 1] RETRY HandshakeAck try=4
[conn 1] RETRY HandshakeAck try=5     ← 재시도 상한에 걸려 포기
```

서버는 `HandshakeAck` 을 신뢰 패킷으로 보냈는데 ack 이 안 오니 유실로 판단했다.
14편에서 만든 **재시도 상한(5)이 자기 증폭을 막아준 실제 사례**다.

여기서 둘 중 하나만 하면 안 된다는 게 드러난다.

| | 결과 |
|---|---|
| ack 만 구현 | 나가는 패킷이 없어서 **영영 안 닿는다** |
| 하트비트만 구현 | 헤더의 `ack = 0` 이 "0번을 받았다"는 **거짓말**이 된다 |

**ack 은 독립적인 패킷이 아니라 나가는 패킷에 얹히는 것**이라, 보낼 일이 없으면 존재할 수
없다. 서버에서 `piggyback` 을 당연하게 썼는데, 클라를 만들면서 그 전제를 다시 만났다.

## ack 주기가 재전송 횟수를 정한다

하트비트(1Hz)를 넣자 연결은 유지됐는데, 이번엔 `Event` 가 try=5 까지 갔다.

산수가 맞는다. 서버의 `rto_ms()` 는 100ms 에서 출발하고, 우리 ack 은 **최대 1초 뒤**에
출발한다. 그 사이 서버는 다섯 번 다시 보내고 포기한다. **클라가 말을 적게 할수록 서버가
헛수고를 한다.**

입력을 30Hz 로 보내기 시작하자 그대로 사라졌다.

| | ack 1Hz | ack 30Hz |
|---|---|---|
| `Event` 재전송 | try=5 까지 가서 포기 | `gaveup=0` |
| 유실 판정 | 계속 발생 | `lost=0` |
| `ackrtt` | — | **15.9ms** |

`ackrtt` 15.9ms 가 특히 깔끔하다. 우리가 33ms 마다 보내니 ack 은 평균 **그 절반**인
16.5ms 뒤에 도착한다. 19d 에서 이 값의 이름을 고치며 *"네트워크 왕복이 아니라 상대의 전송
주기가 더해진 값"*이라고 적었는데, **클라 주기를 바꾸니 숫자가 그대로 따라왔다.**
설명이 맞았다는 걸 이제야 실험으로 확인한 셈이다.

## 화면이 보여준 것

**입장 2초** — 초록 점(플레이어) 둘레로 빨간 점 12개가 고리를 이룬다. 반지름을 픽셀로
재니 약 20 유닛. `kSpawnRadius = 25` 에서 2초 동안 `2.5 × 2 = 5` 좁혀온 값과 맞는다.
스폰 코드가 의도대로 돈다는 걸 처음으로 **보았다**.

**7초** — 전부 한 점이다. 좌표를 떠보니 정말로 전부 `(0, 0)` 이다.

```
 1  Player    0     0     0   Down
 2  Monster   0     0   100   Alive
 3  Monster   0     0   100   Alive
 ...
 0  Door     40     0   100   Alive
```

22편에 *"16c 의 몬스터 뭉침이 그대로다 — 한 점에 모여 접촉 피해가 곱해진다"*라고 썼다.
그건 추측이었다. **글자 그대로였다.** 고리에서 출발한 몬스터가 전부 같은 목표(최근접
플레이어)를 향해 직선으로 들어오니 도착점이 하나다. 서로를 밀어내는 힘이 없다.

**딸려 나온 것 하나** — 전멸(`Failed`)한 방에도 **문이 그려진다.** 들어갈 사람이 없는 방의
문이다. 서버가 `Failed` 에서도 문 엔티티를 스냅샷에 넣고 있다.

## 도구가 또 범인이었다 (여덟 번째)

`unity command simulate_key` 로 키를 눌러봤더니 `D` 하나만 눌렀는데 **오른쪽+아래 대각선**
으로 갔다. 보내는 바이트를 직접 들여다보니 정말로 `x=127, y=-127` 이었다. 그런데 w·a·s·d 를
하나씩 다시 눌러보니 이번엔 **전부 `x=0 y=0`** 이고 `isPressed` 도 전부 `False` 였다.

세 번째 시도 때 `Application.isPlaying` 이 **`False`** 였다. 플레이 모드가 꺼진 뒤
에디트 모드의 씬 오브젝트를 읽고 있었던 것이다.

사람이 진짜 키보드로 눌러보니 `x = +6.16, y = +5.16` — `D` 는 오른쪽, `W` 는 위.
**코드는 처음부터 맞았고 검증 도구가 틀렸다.**

같은 세션에서 `docker logs --tail` 함정도 다시 밟았다. 테스트가 끝난 뒤의 구간을 보고
"서버가 아무것도 못 받는다"고 판단했는데, 받은 구간을 찾아보니 `recv 11B (1 pkt)` 가 매 초
정확히 찍혀 있었다. 19a 에서 두 번 당하고 기록까지 해둔 함정이다.

**도구가 틀렸을 가능성을 코드와 같은 순위로 의심해야 한다.** 15b(BOM 없는 PowerShell),
19a(로그 꼬리), 22(루프 초기값)에 이어 네 번째다.

## 거울로 옮긴 것과 옮기지 않은 것

C# 으로 다시 쓴 것은 **헤더 변환 · `sequence_greater_than` · ack 비트 생성 · 스냅샷
읽기**뿐이다. 보낸 패킷 기록(`SentPacket`)도, 재전송도, RTO 도 옮기지 않았다. 클라가 보내는
것 중 신뢰가 필요한 게 아직 없다.

`shift == 32` 를 따로 두는 가지는 그대로 옮겼다. **C# 도 `uint << 32` 가 안전하지 않다** —
C++ 은 미정의 동작이고 C# 은 시프트 수를 31로 마스킹해서 `<< 0` 이 된다. 이유는 다른데
증상은 같다.

반대로 **대각선 정규화는 클라에 넣지 않았다.** 서버가 `len2 > 1.0f` 로 이미 한다. 양쪽에서
하면 `0.707 × 0.707 = 0.5` 로 대각선이 더 느려진다. 한 군데서만 해야 하고, 그 한 군데는
**믿을 수 있는 쪽**이다.

**현재 한계 (의도적):**
- **보간이 없다** — 30Hz 스냅샷을 그대로 찍는다. 끊김을 눈으로 본 뒤에 넣는다.
- **내 엔티티를 모른다** — `HandshakeAck` 이 헤더 11바이트뿐이라 서버가 내 `entity_id` 를
  알려주지 않는다. 화면에서 초록 점이 하나뿐이라 지금은 티가 안 난다.
- **`RoomState` 를 안 읽는다** — 방·웨이브·단계가 화면에 없어서 추측해야 한다.
- **익명 입장** — 토큰 흐름을 건너뛴다. 로비 TCP 클라가 생기면 붙인다.
- **8초면 죽는다** — 긴 관찰이 불가능하다. 24편에서 원인을 치운다.
- **네모 하나로 전부 그린다** — 색과 크기만 다르다.

**검증:** 도커 compose(`BATTLE_ALLOW_ANONYMOUS=1`) + 유니티 에디터 플레이 모드.

1. 헤더 왕복 — `0B-47 02-01 00-02 DE-AD-BE-EF 01`, seq 513 이 `02-01` 로 나감(빅엔디안)
2. 입장 340ms, 서버 로그에 `recv 11B (1 pkt)` — 토큰 없는 핸드셰이크 1개
3. ack 없이 → **정확히 5초 뒤 끊김**, `HandshakeAck` 5회 재전송
4. ack + 하트비트 → 12초 연속 `snap=30`, 서버 `recv 11B (1 pkt)` 매 초
5. 스냅샷 → 스폰 링 반지름 20(= 25 − 2.5×2), 7초 뒤 전원 `(0, 0)`
6. 입력 30Hz → 서버 `recv 390B (30 pkt)` = 13바이트 × 30
7. `sent=3953 acked=3951 lost=0 gaveup=0 ackrtt=15.9ms`
8. 사람이 `D` → `W` → `x=+6.16, y=+5.16`
