# Step 19 — 측정: 추정이 틀린 자리를 찾는다


**Decision:** 바이트를 타입별로 세고(19a), C++ 봇으로 4인을 만들고(19b), 유실을
시뮬레이션하고(19c), 진짜 왕복 시간을 재고(19d), 드러난 것을 고친다(19e).

**Why:** Step 14~18 에서 "나중에 재고 고친다"고 미뤄둔 것이 넷 쌓였다.

| 미뤄둔 것 | 어디서 |
|---|---|
| 몬스터를 몇 마리까지 넣을 수 있나 | 17 (1400바이트 논의) |
| 인원이 늘면 난이도가 제곱으로 쉬워짐 | 18 |
| RTT 가 네트워크 지연이 아니라 ack 지연 | 15 |
| 인플라이트 상한에 밀려 유실 판정도 못 받는 패킷 | 16 |

전부 **"그럴 것 같다"**로만 적어둔 것이었다. 재보니 둘은 맞았고, 하나는 생각보다 **훨씬
가까웠고**, 하나는 **이름만 고치면 되는 문제**였다.

**Alternatives considered:**
- **PowerShell 클라이언트를 계속 쓰기**: 새로 만들 게 없다. 그런데 30/s 를 목표로 했는데
  **21/s** 밖에 못 보냈다. 측정 도구가 측정 대상을 왜곡하면 숫자가 무의미하다.
- **봇이 `Connection` 을 재사용하기**: 코드가 준다. 그런데 ack 생성을 공유하면 **서버가
  틀렸을 때 봇도 같이 틀려서 못 잡는다.** 테스트가 구현을 복제하면 거울이 된다.
- **지연(latency) 시뮬레이션도 만들기**: 보낼 패킷을 복사해 들고 있다가 타이머로 내보내야
  하는데, 버퍼 하나를 돌려쓰는 구조와 안 맞는다. 그리고 RTO 는 RTT 에 비례하므로 지연이
  늘면 **동작이 느려질 뿐 달라지지 않는다.**

**작은 패킷에서는 봉투가 내용보다 크다.** 와이어 추정치(IP 20 + UDP 8)를 같이 찍게 했더니
수신 쪽이 **3.2배**로 나왔다 — 입력 패킷이 13바이트뿐이라 28바이트 헤더가 지배한다.
"입력을 2바이트 더 넣어도 되나"가 아니라 **"30Hz 를 60Hz 로 올려도 되나"**가 비싼 질문이다.

**안 보이게 만든 것도 셀 수는 있어야 한다.** 13 편에서 "잘못된 패킷에 로그를 안 남긴다"고
했다(포트 스캐너 하나에 로그가 폭발한다). 그런데 **카운터는 뒀다.** 그게 19c 에서 봇 버그를
잡았다 — `dropped 26` 이라는 숫자 하나가 "초당 26개가 등록 안 된 주소에서 온다"를 알려줬고,
`conns 3` 과 연결됐다.

**추정이 가장 많이 틀린 곳은 1400바이트였다.** 17 편에서 "방 10 에서 60마리, 154개까지 한참
남았다"고 적었다. 그런데 그 계산에 **인원수가 빠져 있었다.** 19e 에서 마릿수에 인원수를
곱하고 나니:

```
4인, 방 4, 웨이브 2 → (12 + 16 + 8) × 4 = 144마리
스냅샷 = 1 + 148 × 11 = 1,629B      ← 넘는다
```

**"언젠가"가 "방 4"가 됐다.** 재보기 전에는 압축이 먼 이야기였는데, 재고 나니 다음 작업
후보가 됐다. 추정으로 우선순위를 정하면 이런 걸 놓친다.

**측정이 코드가 아니라 이름을 고치게 한 경우도 있었다.** 서버의 `rtt_ms` 는 루프백에서도
17.84ms 가 나오는데, 봇이 Heartbeat 토큰으로 잰 진짜 왕복은 **0.089ms** 였다. 200배 차이다.

그런데 **RTO 계산은 틀리지 않았다.** ack 는 실제로 "네트워크 왕복 + 상대의 전송 주기" 뒤에
오므로, RTO 는 그만큼 기다려야 맞다. 틀린 것은 `rtt` 라는 이름뿐이었다. 로그를 `ackrtt=` 로
바꾸고 주석을 달았다. 6개월 뒤에 "핑 18ms 네"라고 읽으면 잘못된 결론에 도달한다.

진짜 왕복은 **클라이언트가 잰다.** 서버는 4바이트를 받아 **해석하지 않고 그대로 돌려준다** —
그 값이 밀리초인지 프레임 번호인지 모른다. 덕분에 두 기계의 시계를 맞출 필요가 없고,
클라이언트가 바꾸고 싶으면 서버를 안 고쳐도 된다.

**Step 14 의 신뢰성 계층을 처음으로 유실 환경에서 돌렸다.** 만든 지 다섯 스텝이 지났는데
루프백은 0% 라 한 번도 일한 적이 없었다. 유실률을 넣으니 재전송이 비례해 늘었고(0 → 6 → 25회),
**스냅샷은 한 번도 재전송되지 않았다.** 14c 에서 정한 선택적 신뢰성이 그대로 동작한다.

**여섯 번째로 도구가 범인이었다.**

| Step | 증상 | 진짜 원인 |
|---|---|---|
| 10 | 서버가 멈춘 줄 알았음 | 테스트 클라의 프레임 동기화 깨짐 |
| 13 | 프로토콜 ID 가 `0x0047` | PowerShell `[byte] -shl 8` 이 0 반환 |
| 15 | `move_y` 가 항상 0 | BOM 없는 UTF-8 + 한글 주석 |
| 19a | 서버 `recv` 가 0 | **로그를 `tail` 로 봐서 끝난 뒤의 초만 봄** |
| 19b | 세그폴트 | `std::function` 을 지역에 두고 참조 캡처 |
| 19c | 스냅샷이 예상의 73% | **봇이 핸드셰이크를 재시도 안 함** |

19a 가 특히 민망하다. `--no-cache` 재빌드까지 했는데 코드는 처음부터 멀쩡했고, 필터만 바꾸니
바로 나왔다.

```bash
docker logs b19 | grep "net] sent" | grep -v "recv 0B"
```

`tail` 은 "최근"을 보여주지 **"관심 있는 구간"**을 보여주지 않는다. 테스트가 끝난 뒤 로그를
보면 **끝난 뒤의 초가 최근**이다. 15 편에서 "도구를 의심하라"고 적어놓고, 이번엔 **관측
방법**을 안 의심했다.

19c 는 봇만의 문제가 아니다. **유니티 클라이언트도 "핸드셰이크 한 번 보내고 기다린다"로
짜면 모바일에서 가끔 접속이 안 된다.** 13 편에서 핸드셰이크를 멱등하게 만든 것이 "클라가
재시도할 것"을 전제한 설계였는데, 그 클라를 처음 만들면서 그걸 빠뜨렸다.

**고장났을 때만 켜지는 경로는 검증이 안 된다.** 인플라이트 상한(256)에 밀려난 패킷이 유실
집계에서 사라지던 문제가 그랬다. 정상 상황에서는 상한에 안 걸리므로 **평소엔 아무 문제가
없다.** 그런데 문제가 생겼을 때 "유실률 0%"라고 거짓말을 한다 — 계측이 고장을 가린다.

**현재 한계 (의도적):**
- **지연 시뮬레이션이 없다** — 유실만 넣었다. 지연은 송신 큐가 필요한데, RTO 가 RTT 에
  비례하므로 느려질 뿐 동작이 달라지지 않는다.
- **봇이 한 프로세스에 모여 있다** — 네 봇이 **정확히 같은 순간**에 보낸다. 실제 클라이언트는
  각자의 시계로 흩어져 있어서 버스트가 덜하다. **실제보다 가혹한 조건**이라 괜찮지만, 숫자를
  읽을 때 알고 있어야 한다.
- **CPU·메모리를 안 쟀다** — `docker stats` 로 밖에서 볼 수는 있다. 라즈베리파이에서 재는
  것이 의미 있지 x86 에서 재는 건 별로다.
- **압축을 안 했다** — 방 4 에서 1400바이트에 닿는 걸 알면서도 미뤘다. 실제로 잘려서 몬스터가
  깜빡이는 걸 본 뒤에 한다.
- **몬스터 뭉침은 그대로** — 16c 부터 알고 있었고 18 에서 밸런스 문제가 됐는데 아직 안 고쳤다.
  측정보다 플레이 감각의 문제라 클라이언트가 생긴 뒤가 맞다.

**검증:** 도커 컨테이너 안에서 봇을 실행 (호스트 UDP 포워딩을 거치지 않음).

*계측 (19a)*
1. 1인 기준 송신 4,669B/s (와이어 5,537B/s), 수신 273B/s (와이어 861B/s)
2. 수신 와이어 배율 **3.2배** — 13바이트 입력에 28바이트 헤더
3. `snap peak 144B` = `1 + 13 × 11` 과 정확히 일치

*봇 (19b)*
4. 전송 **30.07/s** (PowerShell 은 21/s)
5. 1 / 2 / 4인 송신(와이어) 5,537 / 11,668 / **26,020** B/s — 인원 4배에 **4.7배**
6. 1인당 비용 5,537 → 6,505 B/s (**17% 증가**) — 스냅샷에 다른 플레이어가 들어가서

*유실 (19c)*
7. 설정 10% → 봇 추정 **9.93%**, 스냅샷 27.05/s (이론 27.0)
8. 설정 30% → 봇 추정 **32.2%**, 스냅샷 20.14/s (이론 21.0)
9. 서버 `RETRY` 0 → 6 → 25회. **스냅샷은 한 번도 재전송되지 않음**

*왕복 시간 (19d)*
10. 진짜 왕복 **0.089ms** vs 서버 `ackrtt` **17.84ms** — 200배
11. 클라 전송 주기를 바꾸면 `ackrtt` 가 따라 움직임 (70ms → 78, 33ms → 18~32)

*수정 (19e)*
12. 1인 12마리 / 4인 **48마리** — 인원수가 난이도에 반영됨
13. 4인 스냅샷 피크 **573B** = `1 + 52 × 11` (예측과 일치)
14. 4인 클라 수신 **60.6 KB/s** (1인 4.05 KB/s 의 **15배**)
