# 테스트


Unity 클라이언트가 아직 없어서, PowerShell 스크립트로 임시 클라이언트를 만들어 쓴다.

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
. .\tools\test-client.ps1
```

`Set-ExecutionPolicy`는 현재 창에만 적용되고 창을 닫으면 원복된다.
dot sourcing(`. ` 접두사)으로 불러와야 함수가 현재 세션에 남는다.

| 함수 | 용도 |
|---|---|
| `New-Client` | 연결 하나를 열고 스트림을 돌려줌. 여러 번 불러서 한 창에서 여러 명을 흉내낼 수 있음 |
| `Send-Framed` | 길이-prefix를 붙여 전송 |
| `Read-Framed` | 한 개를 읽음. 올 때까지 블로킹 |
| `Read-Available` | 지금 도착해 있는 것만 전부 읽음. 브로드캐스트 확인용 |
| `Close-Clients` | 열어둔 연결 전부 닫기 |

```powershell
$alice = New-Client
$bob   = New-Client

Send-Framed $alice '{"type":"Login","data":{"username":"alice"}}'
Send-Framed $bob   '{"type":"Login","data":{"username":"bob"}}'
Read-Available $alice
Read-Available $bob

Send-Framed $alice '{"type":"RoomCreate","data":{"name":"Boss Room"}}'
Send-Framed $bob   '{"type":"RoomJoin","data":{"roomId":1}}'
Read-Available $alice     # bob이 들어온 걸 alice도 통보받는다

Send-Framed $alice '{"type":"ChatSend","data":{"text":"bob 왔냐"}}'
Read-Available $bob
```

`Read-Framed`는 메시지가 올 때까지 멈춰 있어서 브로드캐스트 확인에 쓰기 어렵다.
서버가 언제 몇 개를 밀어줄지 모르기 때문에, 도착해 있는 것만 꺼내는 `Read-Available`을 쓴다.

**알려진 한계 — 프레임 동기화가 깨질 수 있다.** `Read-Available`은 `DataAvailable`로 "읽을 게
있나"만 보고 `Read-Framed`에 들어간다. 그런데 TCP는 메시지 경계를 보장하지 않으므로(Step 4),
큰 응답이 여러 세그먼트로 쪼개져 오면 프레임 한가운데서 읽기가 멈출 수 있다. 그 상태로 다음
읽기를 하면 본문 중간의 4바이트를 헤더로 착각해 **이후 전부 어긋난다** — 출력에서 정확히
4바이트씩 사라진 JSON 조각이 나오는 게 그 증상이다.

방어책으로 `New-Client`가 `ReadTimeout`을 걸고, `Read-Framed`가 길이 상한(1MB)을 검사하고,
`Read-Available`이 예외를 만나면 그 연결을 닫는다. **멈추거나 조용히 틀린 결과를 내는 대신
시끄럽게 터지게** 하는 것까지가 목적이다. 서버가 Step 4에서 길이 상한을 둔 것과 같은 이유.

제대로 고치려면 수신 버퍼를 따로 두고 완전한 프레임이 모였을 때만 꺼내야 한다 — 서버가
`async_read`로 하는 일이다. 임시 도구에 그건 과하다고 판단해서, 대신 **응답이 커지는 시나리오
(방이 여러 개인 상태에서 `RoomList` 반복 조회 등)는 피해서 테스트를 짠다.** Unity 클라이언트는
비동기 수신 + 버퍼 구조로 만들 것이므로 이 문제가 없다.

스크립트 파일은 **UTF-8 with BOM**으로 저장해야 한다. Windows PowerShell 5.1은 BOM이 없으면
`.ps1`을 시스템 ANSI 코드페이지(한국어 환경이면 949)로 읽어서, 한글이 들어간 경로나 문자열이 깨진다.

### 부하 테스트 — C++ 봇

PowerShell 클라이언트는 **초당 30개를 보내려다 21개만 보냈다.** 스크립트 자체가 병목이라
측정 도구로 쓸 수 없다. 봇은 서버와 같은 `Protocol.cpp` 를 쓰고, 틱도 `expires_at` 으로
걸어서 **30.07/s** 를 지킨다.

```bash
docker run -d --name b19 coop-dungeon-battle
docker exec b19 ./battle_bot 4 15        # 봇 4명, 15초
```

봇을 서버와 **같은 컨테이너 안**에서 돌리면 호스트의 UDP 포트 포워딩을 거치지 않아 측정이
깨끗하다. 밖에서 쏘려면 `BOT_HOST` / `BOT_PORT` 를 준다.

```
--- 결과 ---
true rtt  0.118839ms 평균 (min 0.019 / max 0.252) 표본 112
sent      1792 pkt (32/s/bot)
recv      1924 pkt, 868692 B (60.5951 KB/s 전체)
snapshots 1680 (30/s/bot)
entities  45.7024 평균
gaps      0 (0% 추정 유실)
max payload 573B
```

**ack 생성만큼은 서버 코드를 재사용하지 않는다.** `Connection::on_packet_received` 를 그대로
쓰면 서버가 틀렸을 때 봇도 같이 틀려서 못 잡는다. 직렬화(`Protocol.cpp`)는 "양쪽이 같아야
맞는 것"이라 공유해도 되지만, **판단 로직은 따로 짜야 검증이 된다.**

봇의 유실률은 **추정치**다. 번호가 건너뛰면 일단 유실로 세고, 나중에 도착하면 되돌린다.
32칸 창을 벗어나 도착한 건 못 되돌리므로 **실제보다 나쁘게 나올 수 있다** — 안전한 쪽 오차다.

### 유실 시뮬레이션

루프백은 유실이 0%라, Step 14 의 신뢰성 계층을 **실제 유실 환경에서 돌려본 적이 없었다.**

```bash
docker run -d --name b19 -e SIM_LOSS_IN=30 -e SIM_LOSS_OUT=30 coop-dungeon-battle
```

| 설정 | 봇 추정 유실 | 스냅샷/s (이론) | 서버 RETRY |
|---|---|---|---|
| 0% | 0% | 30.0 (30.0) | 0 |
| 10% | 9.93% | 27.05 (27.0) | 6 |
| 30% | 32.2% | 20.14 (21.0) | 25 |

유실률에 비례해 재전송이 는다. 그런데 30% 유실 구간에 나간 스냅샷 약 1,680개 중 **재전송된
것은 없다** — `RETRY` 25회는 전부 `Event` 다. 14c 의 선택적 신뢰성이 그대로 동작한다.

유실은 `send_to` 에서 `on_packet_sent` **뒤에** 버린다. 순서가 반대면 신뢰성 계층이 그 패킷을
모르고, 유실 탐지도 재전송도 일어나지 않는다. 실제 네트워크에서도 `sendto` 는 성공하고
패킷은 중간에서 사라진다 — **애플리케이션은 보냈다고 믿는다.**

서버와 봇 모두 **고정 시드**를 쓴다. 같은 조건이면 같은 패킷이 사라지고 봇이 같은 길로
움직인다. 측정에서는 남길 변수를 하나로 줄여야 한다.

### 측정 결과

**1인 → 4인에서 트래픽이 15배가 된다.**

| | 1인 | 4인 |
|---|---|---|
| 서버 송신 (와이어) | 5,537 B/s | 26,020 B/s |
| 클라 수신 총량 | 4.05 KB/s | **60.6 KB/s** |
| 스냅샷 피크 | 144B | **573B** |
| 엔티티 평균 | 11.3 | 45.7 |

스냅샷 바이트는 `(엔티티 수) × (인원 수)` 로 자란다. **인원이 늘면 제곱으로 늘어난다.**

`573B` 는 `1 + 52 × 11` 과 정확히 맞는다. 그리고 4인 기준으로 계산하면 **방 4 부근에서
1400바이트에 닿는다.**

```
4인, 방 4, 웨이브 2 → (12 + 16 + 8) × 4 = 144마리
스냅샷 = 1 + 148 × 11 = 1,629B      ← 넘는다
```

17 편에서 "154까지 한참 남았다"고 적었던 것이, 인원수를 반영하니 **던전 중반**의 일이 됐다.

**와이어 오버헤드가 작은 패킷에서 지배적이다.** IP(20) + UDP(8) = 28바이트가 패킷마다 붙는다.

| | 본문 | 와이어 | 배율 |
|---|---|---|---|
| 송신 (스냅샷 위주) | 4,669 B/s | 5,537 B/s | 1.19× |
| 수신 (입력 13B) | 273 B/s | 861 B/s | **3.2×** |

입력을 2바이트에서 4바이트로 늘려도 와이어는 41B → 43B(5%)지만, 30Hz 를 60Hz 로 올리면
**두 배**다. **크기보다 빈도가 비싸다.**

### `ackrtt` 는 핑이 아니다

서버가 재는 `rtt_ms` 는 **ack 가 돌아오기까지의 시간**이고, 거기에는 상대의 전송 주기가
통째로 들어간다. 봇이 Heartbeat 토큰으로 잰 진짜 왕복과 비교하면 드러난다.

```
진짜 왕복 : 0.089ms  (루프백)
서버 ackrtt: 17.84ms
```

**200배 차이**다. 클라이언트 전송 주기를 바꾸면 `ackrtt` 가 따라 움직인다(PowerShell 70ms →
78ms, 봇 33ms → 18~32ms).

RTO 용도로는 이 값이 **맞다** — ack 는 실제로 그만큼 뒤에 온다. 틀린 것은 이름이었고, 그래서
로그 이름만 `ackrtt=` 로 바꿨다. 화면에 "핑"으로 띄우려면 클라이언트가 직접 재야 한다.

서버는 Heartbeat 의 4바이트를 **해석하지 않고 그대로 되돌려준다.** 그 값이 밀리초인지
프레임 번호인지 모르고 알 필요도 없다. 덕분에 **두 기계의 시계를 맞출 필요가 없다** —
클라이언트가 자기 시계를 두 번 볼 뿐이다.

되돌려주는 크기에는 상한(`kHeartbeatPayloadSize`)을 둔다. 1400바이트를 받아 1400바이트를
돌려주면 증폭 공격의 재료가 된다.
